# 03 持久化执行与审批恢复

## 一、总述：事件事实、状态投影和外部副作用分别管理

核心采用事件驱动的持久化状态机。每次确认推进在同一事务中追加执行事件、更新状态投影和写入必要 outbox；快照加速恢复，事件保留可解释轨迹。先落实运行域，不将全平台所有数据都改为事件溯源。

事件保存业务决策、模型请求/响应的受控引用、工具调用状态和结果摘要，不要求记录模型内部思维链。上下文 Delta 需要序号、基础版本与校验；定期快照避免无限重放。

## 二、任务推进与外部调用

任务固定技能 Revision、输入版本和运行定义，状态包括 READY、RUNNING、WAITING_EXTERNAL、WAITING_RETRY、NEEDS_RECONCILIATION、SUCCEEDED、FAILED、CANCELLED、REJECTED、EXPIRED。

| 步骤 | 提交内容 | 失败后的恢复方式 |
|---|---|---|
| 接入 | 去重后的任务与初始事件 | 重复消息返回已有任务 |
| 认领 | 执行者、租约期限、世代和步骤版本 | 租约过期可重新认领，旧结果不得覆盖新世代 |
| 准备上下文 | 授权后证据引用、技能版本与输入摘要 | 原材料版本核对，权限重新校验 |
| 请求模型 | 请求意图、预算及尝试标识；响应确认后保存引用 | 请求结果未知可能再次计费，记录重复尝试；不承诺模型可确定性重现 |
| 解析动作 | 结构化动作、参数和规则检查结果 | 不合法动作停止或在预算内纠正 |
| 调用工具 | 调用意图、操作键、批准版本，随后记录外部结果 | 结果未知先核对，不能盲目重发高风险写入 |
| 完成与通知 | 最终结果与交付 outbox | 通知失败独立恢复，不重做已完成业务步骤 |

网络调用、模型推理、文件解析与审批等待均在数据库事务外进行。状态条件更新与唯一操作键防止重复推进，队列通知仅是提示，任务表与事件才是事实源。

外部调用窗口分为“未发出、已发出未知、已确认”。只有可证明未发出或具备可靠幂等机制时才自动重试写入。结果查询不可用时转 NEEDS_RECONCILIATION；即便旧执行者失去租约，其已发出的外部请求仍可能成功，不能用本地 fencing 宣称已撤销副作用。

## 三、审批挂起与恢复

1. 命中特批后固定报价版本、计算依据、规则、审批范围和有效期，在事务中写入 WAITING_EXTERNAL、审批记录与卡片 outbox。
2. 生成不可预测且限定用途的 Resume_Token 或等价恢复引用；只保存必要验证信息，不将可恢复任务的敏感令牌写入公开日志。
3. 提交后释放执行协程。等待由持久化状态、定时检查和回调驱动，不保留原调用栈。
4. 回调到达时验证渠道真实性、审批人身份、权限、任务状态、有效期与内容版本；Token 只是关联凭据，不是批准权限。
5. 在同一事务中消费有效回调、追加审批事件并创建恢复任务。重复回调返回已有决策，不多次唤醒业务效果。
6. 主管修改单价时创建新报价版本，重新核价与检查审批范围；符合其权限后批准新版本，否则转相应审批。旧卡片及旧批准不得套用。
7. 任意合格执行节点恢复任务，真正写入与交付前重验当前授权；批准不意味着正式用章或对外发送已获授权。

等待期间仍有数据库记录、扫描、提醒与审计成本，“零资源消耗”仅可理解为无专属执行协程驻留。审批超时按规则提醒、升级或过期，永不自动批准。

## 四、恢复、补偿与版本演进

可恢复计算失败按有界退避重试；不可恢复输入或配置错误返回待补充/失败；超限进入人工处理。取消阻止未执行动作，对已经成功的业务动作依据补偿定义处理，补偿本身也需授权、幂等与审计。

运行时区分重放与重执行：重放使用已记录的模型/工具结果构建状态，不再次调用真实写接口；缺少记录时只报告缺口，不能为了重建轨迹偷偷执行外部业务。

V1 在途任务默认使用 V1 技能和规则引用，新任务使用 V2；安全授权仍取当前有效值。运行定义、事件格式、快照格式和工具契约分别版本化。新运行时须支持仍存活的旧版本，或先暂停并完成显式迁移；回滚前验证旧程序可读新数据，不假设二进制回退必然安全。

外层状态机强制审批和价格红线，内层 Agent 可在工具白名单、步数、成本和时长预算内探索。自愈不允许变更权限、规避审批或切换到未批准模型。
