# 02 用户场景与业务闭环

## 一、总述：围绕报价任务建立闭环

核心场景是销售通过飞书群提出：“根据刚刚和 A 公司的会议纪要生成定制报价单初稿，折扣低于八折时走特批。”系统完成授权、取证、核价、审批和交付；不能把生成内容视为已获准对外使用。

角色包括销售、客户负责人、销售主管、价格规则维护者、用章或正式发布责任人、平台运维与审计人员。角色可由同一自然人承担，但授权动作和审计记录仍须区分。

## 二、前置条件与业务规则

企业需配置身份对应关系、客户与项目权限、定价口径、审批人及代理规则、报价模板、有效期和允许交付的对象。CRM 负责人关系只是可能的授权依据，最终以企业授权规则为准，不能仅凭模型判断放行。

示例规则为：有效折扣 = 同范围、同币种、同税费口径的成交价合计 ÷ 标准价合计；低于 0.80 触发特批，恰好 0.80 不因本条触发特批。实际税费、阶梯价、运费、舍入、汇率时点和最低毛利等规则由企业批准后配置。标准价缺失或分母为零时不得给出有效折扣判断。

报价版本应关联输入证据、价格目录版本、计算结果和适用规则。审批人修改任一影响金额或风险的字段，必须形成新版本并重新核算、检查审批范围；不得将旧版本批准套用到新内容。

## 三、主流程：上一步产出驱动下一步

| 步骤 | 输入与执行行为 | 输出及后续依赖 |
|---|---|---|
| 1 接入与身份识别 | 校验消息来源，识别发起人、组织、租户与会话；映射企业员工身份 | 可信身份与任务记录，供所有后续授权使用 |
| 2 意图与技能匹配 | 加载报价技能摘要并匹配需求；信息不足时询问产品、数量、客户或纪要范围 | 确定任务范围与技能版本，后续执行固定使用该版本 |
| 3 授权取证 | 在允许范围内获取会议纪要、CRM 历史成交记录和产品目录；群聊上下文只读取获准范围 | 带来源、时效和权限信息的证据集；不足则补充或转人工 |
| 4 精确核价 | 使用受控计算能力处理阶梯价格、折扣和毛利；模型解释结果但不替代算术规则 | 可复算报价初稿与风险判断，例如有效折扣 0.75 |
| 5 特批与持久化等待 | 命中特批后固定报价版本、摘要、差异和风险；向有权主管推送卡片 | 审批待办与可恢复状态，等待不依赖持续存活的执行进程 |
| 6 决策与修改 | 例如三小时后主管点击批准并调整某项单价；验证审批身份、有效期及版本 | 修改则重新核价；符合其审批权限后批准新版本，否则转相应审批人 |
| 7 文件生成与授权 | 根据批准版本生成 PDF；初稿、审批通过稿和正式文件分别标识 | 可追溯文件；公章水印仅在用章授权满足后添加 |
| 8 安全交付与结束 | 校验原群成员或接收对象是否均可查看；记录文件版本、接收范围和交付结果 | 合法范围内交付；不适合群发时以私聊或受权限保护链接交付，并在原群仅报安全状态 |

低风险正常报价可跳过本条特批等待，但仍须通过企业其他审核与正式发布规则。用户仅请求初稿时，最终自动化范围不能自行扩展为对客户发送或正式用章。

审批卡片展示客户背景、会议纪要摘要、报价前后差异、折扣与毛利测算、来源入口和决策按钮。卡片本身也受权限控制，无权读取完整背景的审批人应按规则转派，不通过展示卡片绕过知识权限。

## 四、状态与异常收口

业务状态包括：已接收、待补充、执行中、待审批、待核对、已批准待交付、已完成、已拒绝、已取消、已过期、失败待处理。已完成表示预定交付动作完成，不表示所有潜在后续销售流程完成。

| 情况 | 必须行为 | 收口结果 |
|---|---|---|
| 找不到纪要或读取被拒绝 | 不泄露不可见文档名称和摘要；请求用户提供其有权提交的材料 | 待补充或转人工 |
| 来源冲突、过期或价格缺失 | 明确冲突和不确定性；不编造价格或默默选择口径 | 待核对 |
| 主管拒绝 | 保存理由并通知销售，不生成正式批准文件 | 已拒绝；修订后作为新版本重新申请 |
| 审批超时 | 按企业配置提醒、升级或过期；不得默认批准 | 待审批或已过期 |
| 主管修改报价 | 新版本重新计算和检查所有规则；旧卡片失效 | 新审批或经授权批准的新版本 |
| 重启或执行节点故障 | 从已确认步骤继续，读取已固定的技能与业务版本 | 恢复执行，既有批准不丢失 |
| 写入请求超时且结果未知 | 先查询业务结果；不能核实时禁止盲目重试 | 待核对，由责任人确认 |
| 重复消息、重复回调或过期卡片 | 去重并验证任务、审批人、版本与当前状态 | 返回已有结果或明确拒绝，不重复发单/发送 |
| 执行期间撤销权限或员工离职 | 下一次读取、执行、审批或交付前重新授权 | 停止相关动作并交由有权人员处理 |
| 用户取消 | 阻止尚未执行的动作；已发生动作按业务补偿规则处理 | 已取消或待补偿，不伪称已撤回全部影响 |
| 已写入 ERP 后文件生成失败 | 保留已成功业务结果，单独重试允许的生成步骤 | 不重复建单；必要时人工补偿 |
| 群成员变化或存在无权成员 | 禁止在群内输出敏感正文或无保护附件 | 私聊/受控链接；不可安全交付则待处理 |

## 五、扩展场景：复用同一执行与治理链路

| 场景 | 业务步骤 | 人工边界与产出 |
|---|---|---|
| 产研协同 | 飞书/钉钉报错群取证→关联 GitLab 提交、Jira 工单与 ELK 日志→提出原因假设和责任团队 | 给出证据与置信限制；生产修改、回滚和通知责任人按授权处理，不凭推测归责 |
| 财务/法务合规 | 合同条款提取→与企业红线库比对→结合企查查/天眼查等获准资信信息→生成差异报告 | 标注条款位置、来源日期和风险；法务作最终判断，报告不自动等同签约批准 |
| 外贸/供应链跟单 | 多语种邮件/Excel 询盘解析→查询 ERP 库存与获准汇率源→生成回复与报价草稿→卡片确认 | 处理缺失单位、币种和库存时效；业务员确认后才执行被授权的外部发送 |
| 混合经营分析 | 查询 Q3 华东大客户流失率指标→获取可见客诉纪要→关联分析→给出可追溯解释 | 指标采用企业定义，原因分析区分证据与推断，不将相关性写成已证实因果 |

这些场景共用“身份→授权证据→技能与工具→规则检查→必要审批→安全交付→审计”链路，差异集中在业务口径、连接对象和风险规则。
