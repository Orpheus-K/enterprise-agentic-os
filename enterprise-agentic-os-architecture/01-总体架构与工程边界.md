# 01 总体架构与工程边界

## 一、总述：模块化单体是开发边界，进程角色是部署边界

Go 核心采用模块化单体，以稳定的业务契约隔离身份、运行时、技能、工具、知识和运营。轻量部署将多数模块放在同一进程，生产部署运行同一制品的不同角色。Python 计算面作为独立能力服务，两者不复制业务状态机。

“控制面与执行面分离”首先体现职责与授权；不是要求每个模块都是微服务。管理配置、Go 执行调度和 Python 计算是三种职责，不应把全部 Go 模块统称为纯控制面。

## 二、语言、制品与部署角色

| 层 | 选型 | 责任 | 不承担的责任 |
|---|---|---|---|
| 核心与网关 | Go | IM 接入、API、IAM、策略校验、运行时、MCP 网关、连接池、任务调度 | 不在业务模块嵌入特定数据库实现，不直接执行不可信 Python |
| 能力 Worker | Python＋gRPC | PDF/Office 布局解析、Embedding、重排、算法计算 | 不拥有任务主状态，不签发批准，不持有跨租户业务凭证 |
| 控制台 | TypeScript＋React＋Vite；shadcn/ui＋Tailwind CSS | Skills 管理、权限配置、轨迹排错、审批追踪、ROI 看板 | 客户端渲染，不采用 Next.js/SSR；不在前端作最终授权，不持有服务密钥 |
| 静态制品 | Go embed | 将控制台产物打包进入 Go 制品 | 不承诺包含运行中的 Python、数据库和模型 |

前端基线采用 React 客户端 SPA，以 Vite 构建静态资源，交由 Go embed 提供服务；不采用 Next.js、SSR 或常驻 Node 服务。Node 与前端包管理工具仅用于开发和构建。Go 配置 SPA 路由回退以支持深层地址刷新，API 和静态资源错误不得被错误回退为页面 HTML。[shadcn/ui 的 Vite 接入](https://ui.shadcn.com/docs/installation/vite)与 [Tailwind 的 Vite 集成](https://tailwindcss.com/docs/installation/using-vite)作为实施参考。

进程角色规划为 all-in-one、gateway/api、scheduler/executor 和 compute-worker。前三者复用同一 Go 代码与制品，最后一类为 Python 制品。角色启动须校验驱动、版本和依赖能力，配置错误直接阻断，不静默降级权限或持久化能力。

### 2.1 组件颗粒度与视觉规范

采用 shadcn/ui 作为基础组件来源，以 Tailwind CSS 和统一语义化设计 Token 管理颜色、字体、间距、圆角、边框及状态。视觉参考 Vercel UI：黑白灰中性色、清晰排版、细边框、克制阴影与动效，强调内容层级和信息密度；亮暗主题保持一致，风险、错误和成功状态保留明确语义，不只依靠颜色传达。视觉方向不引入 Vercel 托管或运行时依赖。

组件按“基础 UI → 通用组合 → 业务组件 → 页面”分层：按钮、输入与弹窗等基础组件统一维护；表格工具栏、空状态和确认面板形成可复用组合；审批差异、执行轨迹和技能版本卡片留在业务域。页面负责组合与数据协调，不复制基础样式；基础 UI 不依赖业务 API。按实际复用与职责封装，避免巨型页面和为每个标签创建无意义包装。

优先使用官方维护或社区成熟、文档与类型完善的开源方案，减少重复实现表格、表单、路由、数据请求和无障碍交互。引入前检查维护状态、许可证、安全记录、体积及离线可用性；需要时通过薄适配隔离外部依赖。shadcn/ui 引入的组件源码纳入本仓库版本管理，保留上游来源与本地改动记录。保留键盘导航、焦点管理和可访问名称，不为视觉效果破坏交互语义。

### 2.2 Monorepo 工程组织

Go、Python、前端及契约放在同一仓库，统一变更审查与 CI，分别保留各语言的构建、依赖锁定和测试工具。前端采用 pnpm workspace；不要求将 Go/Python 纳入 JavaScript 依赖管理，也不为 Monorepo 默认增加分布式构建服务。

建议目录边界如下，仅为架构约定，本轮不创建代码脚手架：

```text
apps/web/              # React SPA；业务域组件、页面与路由
services/core/         # Go 核心、网关与执行角色
services/compute/      # Python 能力 Worker
packages/ui/           # shadcn/ui 基础组件、通用组合、主题与设计 Token
packages/api-client/   # 前端类型化 API 客户端
packages/config/       # 前端共享类型检查、代码规范配置
contracts/             # 跨语言接口契约及版本
deploy/                # 部署配置与制品构建入口
docs/                  # 正式工程中的文档归档目录
```

依赖方向为应用消费共享包，共享 UI 不反向依赖应用；禁止包间循环依赖及绕过公开入口导入内部实现。CI 按变更影响执行检查，契约和共享包变更覆盖其消费者；先构建前端再嵌入 Go，最终制品验证资源齐全。共享 UI 的组织方式参考 [shadcn/ui Monorepo 文档](https://ui.shadcn.com/docs/monorepo)。现有两套文档目录保持原位，未来建仓时再统一归档。

## 三、模块依赖与状态所有权

| 模块 | 所有权 | 主要输出与依赖 |
|---|---|---|
| Identity/Policy | 身份映射、有效授权、审批规则引用 | 向知识、工具、运行时提供可信授权判定 |
| Runtime | 任务、步骤、事件、租约、审批关联 | 消费技能版本，调用知识、模型与工具能力 |
| Skill Registry | 技能声明、依赖清单、版本和发布记录 | 输出不可变的运行版本，不授予额外权限 |
| Tool Gateway | 工具定义、映射配置、凭证引用 | 校验后执行工具，向 Runtime 返回结构化结果 |
| Knowledge | 原件引用、解析版本、ACL、索引状态 | 返回有权限的证据和引用，不直接推进业务状态 |
| Model Gateway | 模型能力与路由策略、用量 | 返回模型结果；输出仍须验证 |
| Operations | 审计查询、观测、发布与诊断 | 消费各模块事件，不旁路修改业务事实 |

模块不得直接改写其他模块拥有的表或文件；跨模块操作通过业务契约。需要原子提交的任务状态、执行事件和待发消息由运行时在同一事务单元协调，不能依靠彼此独立的“保存成功”拼接一致性。

执行链路为：IM/API 可信接入→身份及租户解析→任务入库→调度认领→加载固定技能→授权检索→模型计划→工具前校验→审批或执行→结果持久化→交付授权→通知。通知由已持久化的发送意图驱动，不先发送再尝试记录任务。

## 四、跨进程契约与失败边界

Go 与 Python 使用版本化 gRPC 契约，逻辑请求至少关联任务、步骤、租户、输入对象引用、输入摘要、能力版本、截止时间与 Trace_ID。这里定义字段含义，不冻结 protobuf 或 HTTP API；线格式在实施设计中版本化。

大文件通过短时、限范围的对象访问授权传递，避免在 RPC 中反复复制文档。Worker 可使用可清理的临时文件与模型缓存，但不得成为结果唯一持有者；输出先保存至受控对象存储，再由 Go 校验摘要并确认任务结果。

Worker 超时或崩溃只影响当前能力步骤，主状态仍可恢复。长计算不持有数据库事务；按请求标识处理重复提交，迟到响应必须校验任务版本及当前租约。取消后不得让迟到结果重新推进已结束任务。

所有客户使用统一发布线、配置化差异和受认证驱动。紧急修复回合并主线；客户专属能力以有边界的连接器或技能实现，不形成未经追踪的核心分支。源码保护与 License 使用签名、完整性校验和交付策略，不把 Go 编译当作不可逆向保证。

## 五、收束：用存储契约支撑部署裂变

只有状态所有权明确，模块才可从单进程拆到多进程而不改变业务含义。下一篇 [存储策略与驱动契约](02-存储策略与驱动契约.md) 定义跨部署保持一致的事务、租约和权限要求。
